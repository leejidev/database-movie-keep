# MovieKeep 데이터베이스 실습 정리

## 1. 새로고침 후 Firebase 데이터를 Store에 다시 반영하는 이유

새로고침하면 메모리에 보관한 Store의 사용자 정보와 찜 목록이 초기화되기 때문에 Store에 다시 반영해야 기존 찜과 메모를 화면에 표시할 수 있습니다.

TODO 01에서 Firebase가 확인한 로그인 사용자를 `setUser`로 반영하고, TODO 02에서 해당 사용자의 찜 목록을 조회해 `setFavorites`로 반영하는 부분이 이에 해당합니다.

## 2. DB 저장 성공 후 Store를 갱신하는 이유

DB에 저장해도 Store가 자동으로 갱신되지는 않기 때문에 저장 성공 후 Store에도 반영해야 화면과 DB의 데이터를 일치시킬 수 있습니다. Store부터 갱신하면 DB 저장 실패 시 화면과 DB의 데이터가 달라질 수 있습니다.

TODO 03에서 `await updateDoc`으로 저장 성공을 확인한 뒤 해당 찜의 메모를 Store에 반영하는 부분이 이에 해당합니다.

## 3. 빈 메모 저장과 찜 삭제의 차이

빈 메모 저장은 찜 데이터의 `memo`값만 비우기 때문에 찜 상태와 개수가 유지됩니다. `updateDoc`으로 `memo`값을 빈 문자열로 수정하는 부분이 이에 해당합니다.

찜 삭제는 찜 데이터 자체를 제거하기 때문에 찜이 해제되고 찜 개수도 1개 감소합니다. `deleteDoc`으로 해당 찜 문서를 삭제하고 Store에서도 해당 데이터를 제거하는 부분이 이에 해당합니다.

## 4. 복합 UNIQUE와 외래 키의 역할

복합 UNIQUE는 지정한 값의 조합이 같은 데이터의 중복 저장을 방지합니다. TODO 12에서 `UNIQUE (userId, movieId)`로 설정했기 때문에 동일한 사용자가 같은 영화를 중복으로 찜할 수 없습니다. 같은 영화라도 `userId`값이 다르면 조합이 다르므로 저장할 수 있습니다.

외래 키는 다른 테이블에 존재하는 데이터를 참조하도록 제한합니다. TODO 13에서 `favorites` 테이블의 `movieId`값이 `movies` 테이블의 `id`값을 참조하도록 설정했기 때문에 존재하지 않는 영화는 찜할 수 없습니다. 현재 설정에서는 해당 영화를 참조하는 찜 데이터가 있으면 영화 삭제도 불가능합니다.

## 5. 전체 집계와 사용자별 집계의 차이

전체 집계는 조건에 해당하는 데이터 전체를 `COUNT(*)`로 계산합니다. TODO 15에서는 `memo`값이 빈 문자열인 데이터가 총 2개이므로 `emptyMemoCount`값이 2인 결과 한 행을 반환합니다.

사용자별 집계는 조건에 해당하는 데이터를 `GROUP BY userId`로 묶은 뒤 사용자마다 개수를 계산합니다. TODO 16에서는 빈 메모인 데이터가 `user-a`와 `user-b`에 각각 1개씩 존재하므로 사용자별 개수가 1인 결과 두 행을 반환합니다. 이 때 `user-c`는 빈 메모인 데이터가 없으므로 결과에 포함되지 않습니다. `GROUP BY`로 묶기 전에 `WHERE memo = ''` 조건으로 데이터를 선택하기 때문입니다.

## 6. API 개수를 배열 길이로 계산하는 이유

API가 반환하는 찜 목록과 개수를 일치시키기 위함입니다. `favorites` 배열을 데이터로 사용하므로 배열의 길이가 현재 찜 데이터의 개수이기 때문입니다.
